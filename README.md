# 验证不可靠系统的输出 · 两个案例

同一套方法用在两类完全不同的系统上：

| 案例 | 系统类型 | 核心数字 |
| --- | --- | --- |
| **业务文档问答 Agent** | LLM（行为不确定） | 38 条分层用例全通；冲突检测 4/6 → 6/6 |
| **领英抓取流水线**（`linkedin-eval/`） | 规则系统（行为确定但会静默失效） | strong 97.9% vs weak 20%，噪音率 1.9% |

两件事的共同点不是"做得更好"，而是**先知道现在有多好**。

# 案例一：业务文档问答 Agent · 工具循环 + Trace + Eval

一个手写的 agentic loop，配上可复现的评测集。**零第三方依赖**（标准库 + numpy），
DeepSeek 通过 urllib 直连，不需要 `pip install` 任何东西。

> 目的不是"再做一个 RAG demo"，而是回答一个问题：
> **改完之后，到底有没有变好？** 所以第二半（Eval）比第一半（Agent）更重要。

## 知识库是什么

`corpus/` 下 18 篇业务文档，全部来自真实工作产物，已脱敏（去掉人名、公司名、活动名、酒店名）：

| 文档 | 内容 |
| --- | --- |
| 01-领英抓取工作流 | 三段筛选逻辑、geoUrn 参数、7 个踩过的坑 |
| 02-跟进台账使用说明 | 字段定义、状态流转口径 |
| 03-付费判定规则 | 5 条顺序判断树 + 4 条禁止项 |
| 04–11 案例研究 | 微信批量触达系统：三个前提、四个决策、真实数据、失败分类、演进、迁移 |
| 12–17 SOP 六篇 | 日常四步、优先级与状态、付费判定、数量红线、英文话术、收工清单 |
| 18-数据看板口径 | 漏斗各环节的公式与字段定义 |

问的问题是业务问题，不是文档排版问题：

> 问：赞助商推荐来的客户要不要收费？
> 答：按赞助商权益条款执行（判断树第 3 条），不自行承诺免费 [03-付费判定规则.md#1]

**SOP 与台账、看板之间存在真实冲突**（这是企业知识库的常态，不是设计失误）：
「账号通过率」在 SOP 里是 ÷ 已发邀请、在看板公式里是 ÷ 名单总数；
「已通过」在看板里用 `COUNTIF(状态,"已建联")` 统计，而 SOP 里这是两个不同状态。
这些冲突被留在语料里，用来测 Agent 会不会自己挑一份当答案。

## 三个数字

| 指标 | baseline | 说明 |
| --- | --- | --- |
| 主集通过率 | **38/38（100%）** | 32 条分层 + 6 条高难，已饱和 |
| 冲突检测 | **4/6 → 6/6** | 加"必须指出冲突"规则后 +2 条 |
| 检索 hit@1 / hit@3 | **80.6% / 90.3%** | 检索是瓶颈：19% 的题对的段落排到了后面 |

**结论：主集已饱和。** 全通说明语料和题目都太简单（38 个 chunk、答案都能直接从文档里取），
改任何东西都只会掉分，测不出"变好"。下一步要加「多工具协作 + 长链路」的用例才有区分度——
这是评测本身要迭代的地方，比 agent 的分数更值得讲。

**冲突检测是唯一还有区分度的维度：**

| 用例 | 冲突点 | 改规则前 | 改规则后 |
| --- | --- | --- | --- |
| x001 账号通过率怎么算 | SOP 是 ÷ 已发邀请，看板是 ÷ 名单总数 | ✗ 只报了看板口径 | ✓ 明确指出两种分母 |
| x002 CONNECTED 统计哪个状态 | 看板用 "已建联"，SOP 里这是两个状态 | ✗ | ✓ |
| x006 来源字段填什么 | SOP 说 ENGAGED/TARGET，台账说明说三种英文枚举 | ✗ | ✓ |

代价说清楚：**token 15.9k → 27.6k（+73%），步数 2.8 → 3.7（+32%）**。
为了发现冲突，必须多读几篇文档——准确率是用成本换的。

有价值的不是 100%，是**负例的刁钻程度**：

| 诱导型负例 | 正确行为 | 实测 |
| --- | --- | --- |
| “每家公司的实际平均耗时是多少秒？”（文档只给了 110 秒**硬上限**） | 拒答，并指出上限 ≠ 实测平均 | ✓ |
| “这套流程一共完整运行过多少次？”（文档只说“最近两轮”） | 拒答，列出已知零散轮次，不把“最近两轮”当总数 | ✓ |
| “2025 年营收是多少？” | 拒答，并列出实际有什么（送达数据、台账字段） | ✓ |

还有一条区分度高的正例：问“weak 层该保留还是删掉”，文档写的是「暂留候补」，
而评测结论是「该删」—— agent **严格按文档答「保留」**，没有把外部结论混进答案。

## 四个设计决策（每条都放弃了更省事的做法）

**1. 手写循环，不用 LangChain**
框架会把这个循环藏起来。问"终止条件你是怎么定的"时，调框架的人只能答"框架管了"。
手写之后四件事必须自己想清楚：模型决策 → 工具执行 → 结果回填 → 终止判断。

**2. 三道终止条件，不只一道**
- 显式 `finish` 工具：模型主动声明完成
- 模型不再发起 tool_use：自然收敛
- 步数 8 / token 60000 硬上限：兜底

前两道都可能失效——模型会反复调同一个工具，或一直不结束。只有第三道是确定性的。

**3. 检索用手写 BM25，没上向量库**
个人项目跑通优先，且 BM25 没有 embedding 费用；
更重要的是**检索层可替换**——只要 `search()` 契约不变，换成向量检索不影响循环。
代价说清楚：BM25 不懂同义词，问"准确率"可能检索不到写着"精度"的段落。

**4. 引用必须可回指**
chunk id 用「文件名 + 序号」（`03-付费判定规则.md#1`）。语料里同名文件不多，
但保留序号仍然必要——评测要能判"引用的是不是期望的那一篇"。

## 目录

```
agent-eval/

  selftest.bat    双击自检，不需要 key
  run.bat         双击交互提问，需要 key
  llm.py          DeepSeek 客户端（urllib，含重试与结构化错误）
  retrieval.py    中文 BM25（字符 bigram）+ 分块
  tools.py        3 个工具 + finish，失败一律返回 is_error
  agent.py        手写循环、并发工具执行、上下文裁剪、三道终止
  trace.py        每步一行 JSONL，可回放
  make_cases.py   从语料生成用例 + 手写业务用例 + 用例自检
  eval.py         跑用例、判定、汇总、与 baseline 对比
  retrieval_eval.py 检索层评测：hit@1 / hit@3 / MRR（0 成本，不需要 key）
  search.py       探路：只检索不回答，判断一个问题语料里有没有答案
  build_corpus.py 把业务文档（docx / xlsx / md）整理成语料
  build_sop.py    把 SOP 拆成语料（含脱敏）

  traces/         每次运行的完整轨迹
```

## 怎么跑

```powershell
# 0. 放 key（二选一）
#    环境变量：$env:DEEPSEEK_API_KEY="sk-..."
#    或者：在本目录建 key.txt，写一行 key

# 1. 自检，不需要 key（验证环境、语料、判定逻辑）
selftest.bat

# 2. 交互提问，需要 key
run.bat

# 3. 跑真 baseline（32 条，几分钟）
python eval.py

# 4. 改一版（prompt / 工具描述 / 检索参数），再跑，看涨跌
python eval.py --out evals\round2.json --baseline evals\baseline.json

# 单条调试，看完整轨迹
python agent.py "付费判定拿不准怎么办" --echo
```

## 评测怎么设计

**三层用例**：`simple`(9) / `boundary`(18) / `hard`(5)。分别看分数——只看总分会把"简单题全对、边界题全错"藏起来。

**负例是这套评测的核心。**
5 条 hard 问的都是语料里根本没有的事（"营收多少""平均成交周期多久"）。
正确行为不是答对，是**明确说找不到**。这类题测的是"不知道时会不会硬编"——
而这恰好是 LLM 应用最容易骗过 demo、最难骗过生产的地方。

**失败分五类**：`no_citation` / `wrong_doc` / `hallucinated` / `refused_wrongly` / `limit_exceeded`。
分类才能指导行动——知道"引用错了"和知道"根本不会拒答"，修的是完全不同的东西。

**用例集自己也要被检查。**
生成用例时先用同一个 BM25 检一遍：期望引用的文档能不能进 top-5。
进不去就标 `sanity=false`——那可能是用例措辞和原文对不上，不能让它污染 agent 的分数。

## 已知边界（写清楚，不装）

**这是原型，不是生产系统。** 它值得看的地方是"有度量"，不是"能上生产"。具体差在哪：

| 缺口 | 现状 | 生产该怎么做 |
| --- | --- | --- |
| 密钥管理 | `key.txt` 明文 / 环境变量（已 gitignore） | Vault、AWS Secrets Manager、K8s Secret + RBAC；短期凭证而非长期 key |
| 并发 | 单进程串行，无并发压测 | 连接池、限流、队列；按租户隔离配额 |
| 成本控制 | 只有单条 token 统计 | 按任务预算硬截断、按租户累计、超限告警 |
| 可观测 | 本地 JSONL trace | 接 OpenTelemetry / Langfuse，接告警；trace 落对象存储而不是本地磁盘 |
| 发布 | 无版本、无灰度 | prompt / 工具描述版本化，灰度 + 回滚；评测结果绑定版本 |
| 多租户 | 无隔离概念 | 语料按租户分区，检索层强制过滤，防跨租户串数据 |
| 安全 | 无 prompt injection 防护 | 工具返回内容当不可信输入；工具侧最小权限 + 写操作人工确认 |
| 数据 | 25 个 chunk | 真实企业知识库大 2–3 个数量级，chunk 策略需重新调 |

**其余技术边界：**
- 语料只有 11 篇 / 25 个 chunk，这个量级上调出来的检索参数不一定可迁移
- BM25 没有语义召回：同义词、跨语言查询会漏
- 单一模型：没做模型对比，所以"选型判断"目前没有数据支撑
- 没有多轮对话：一问一答，会话记忆没做

> 面试被问"这个能上生产吗"，正确答案不是"能"，是**"我知道差在哪，差的那几块我会按这个顺序补"**。

## 下一轮要改什么（按预期收益排序）

1. **让 agent 学会拒答**：现在 hard 基线预期接近 0%。改 system prompt 的拒答条款 +
   给 `search_docs` 加"无命中即停"的硬约束，预期这是单项收益最大的一改。
2. **加 rerank**：BM25 top-20 → 小模型重排取 top-3，看 `wrong_doc` 是否下降。
3. **工具描述做 A/B**：同一套代码换两版 `search_docs` 描述，看工具选择准确率变化。
4. **补语料**：把发票、报价、SOP 等业务文档并进来，看检索在更大语料上的退化情况。

# 案例二：领英抓取流水线的质量验证（`linkedin-eval/`）

抓了 132 家目标公司在东南亚的联系人，产出 53 条。和案例一不同，这是一个**规则系统**——
三条正则、两层在职判定、一个 geoUrn 过滤。规则系统不会"胡说"，但它会**静默失效**：
跑出来 53 条，看起来都对，没人知道哪几条是错的。

## 怎么量

```powershell
cd linkedin-eval
python label_53.py --make --results sample_results.json   # 生成标注表（带预判）
python label_53.py --analyze                              # 算噪音率、分层准确率、归因
```

判定只有两个选项：该进 / 不该进。说不清的填「不该进」+「信息不足」。

**主指标是噪音率，不是精确率。** 获客名单的业务前提是「宁滥勿缺」——漏一个人比多抓一个人贵。
擦边的（供应链总监、售前顾问）本来就该留，把它们算成"错"会逼你去删不该删的人。
噪音率只算真正的废人。

## 结果

| 指标 | 值 |
| --- | --- |
| 噪音率（完全无关） | **1.9%**（1/53） |
| **strong 层**（有「目前就职」原话可验证） | **97.9%**（47/48） |
| **weak 层**（仅 headline 兜底） | **20%**（1/5） |
| 错误归因 | 职位不对 4 / 完全无关 1 |

## 结论不是"准确率多少"，是"哪一层该删"

97.9% vs 20% 摆在一起，说明 `weak 暂留候补` 这条规则是**负收益**：
为了多抓 5 个候补，顺手塞进 4 个废人。据此应当删掉 weak 兜底，或改成单独输出待确认表。

## 顺手查出两个静默失效

1. **`former` 字段恒空** —— 「剔除已离职」这一环从未真正生效，而且不报错。
   53 条全是"看起来在职"，没有一条经过验证。（根因写在抓取工作流的坑表里：解析时提前 break）
2. **68 条状态停留在旧口径** —— 状态枚举改过，历史数据没迁移。

这两类问题规则系统最典型：**不报错，但结果是错的**。只有统计能发现。

## 边界

- 53 条是单批结果，样本量小，分层结论（尤其 weak 只有 5 条）只能定向参考。
- 召回无法测：不知道漏了谁，只能靠扩大检索源。
- 判定由本人完成，属自证；所以报**相对差异**（strong vs weak）比报绝对准确率更可靠。
- 仓库里只有 10 条脱敏样例；真实数据含姓名与主页链接，不入库。
